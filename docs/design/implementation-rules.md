# 実装ルール

状態: `決定`

## 目的

変更を一つの既存ファイルへ積み増して責務を肥大化させない。仕様と Issue の Acceptance Criteria を、小さく独立してテスト可能なモジュールへ対応付ける。

GitHub Issues が実装対象、優先順位、依存関係の正とする。`docs/` にロードマップ、マイルストーン、重複したバックログは置かない。

## 実装前

- Issue の Goal、Source Spec、Acceptance Criteria、Out of Scope を確認する。
- Source Spec が不足または矛盾する場合は実装せず、仕様を更新して Issue に反映する。
- 変更する既存ファイルごとに、現在の責務と追加する責務を確認する。
- 追加する振る舞いが現在の責務と異なる場合は、先に配置先を決める。配置先のないまま既存ファイルへ追記しない。

## モジュール境界

- `App.tsx` はアプリケーションシェル、フェーズ横断状態の調停、フェーズルーターの配置だけを担当する。フェーズ固有の JSX、`fetch`、入力状態、エラー状態、リトライ処理は置かない。
- フェーズコンポーネントは一つのフェーズの表示とユーザー操作だけを担当する。複数フェーズで使う表示は共通コンポーネントへ切り出す。
- フェーズ固有の通信、ローディング、エラー、リトライ、入力状態は対応する Hook が所有する。Hook は raw setter やアプリ全体の state を返さず、意味のある操作を公開する。
- フェーズをまたぐ遷移、履歴の破棄、セッション保存形式の更新は、横断状態を扱う専用モジュールに集約する。`localStorage` へ直接書き込むコードをフェーズへ置かない。
- frontend と backend の契約は `src/shared/schemas/` を正とする。API 契約の変更は schema、route、client、prompt、テストを同じ変更単位で更新する。
- UI の選択分岐は一か所に保つ。`App` にフェーズごとの大きな render callback や、全 state を詰め込んだ props オブジェクトを置かない。

## 肥大化の防止

- 既存ファイルが 300 行を超えている場合、そのファイルへ新しい責務を追加してはならない。追加前に責務単位で分割する。例外は、分割が可読性を下げる理由と代替案を Issue または PR に明記し、レビューで承認された場合だけとする。
- 既存ファイルが 300 行以下でも、表示、状態遷移、通信、保存、整形のうち二つを超える責務を持つ場合は分割を検討する。新しい変更が三つ目の責務を加える場合は分割を必須とする。
- 新しいファイルは役割を名前で表す。汎用的な `utils.ts`、`helpers.ts`、`common.ts` へ無関係な処理を追加しない。
- 一時的なコメントアウト、未使用の state、開発用の `console.log` を残さない。
- 動作変更と無関係なリファクタリングを同じ Issue に混在させない。分割が動作変更に不可欠な場合だけ、対象を最小範囲に限定する。

## 検証とレビュー

- Acceptance Criteria ごとに、対応する振る舞いテストを作成または更新する。
- state 遷移、保存形式、入力整形は純粋関数または reducer として切り出し、単体テストで保護する。
- UI の分割では、表示条件、無効化条件、エラー、再試行、戻る操作を確認する。
- 変更完了時は `npm run format:check`、`npm test`、`npm run lint`、`npm run typecheck`、`npm run build` を実行する。実行できない場合は理由を Issue または PR に記録する。
