# 仕様書の管理方針

## 採用方針

仕様書は `docs/` 配下を単一の正として管理する。`docs/current/` と `docs/planned/` のような二重構造にはしない。

## 理由

- 確定済み仕様と予定仕様を別ディレクトリに分けると、同じ論点が複数ファイルに分散しやすい。
- 実装前に仕様を更新する運用では、常に「今このリポジトリが正とする仕様」を `docs/` で読めるほうが迷いにくい。
- 未確定事項は仕様本体から消さず、ステータスを明記したほうが実装判断に使いやすい。

## 書き方

各仕様には、必要に応じて次の状態を明記する。

| 状態 | 意味 |
|---|---|
| `決定` | 実装してよい仕様 |
| `検討中` | 仕様検討中で、実装前に確認が必要 |
| `保留` | 今は実装しないが、将来再検討する |
| `MVP対象外` | MVP では実装しない |

## 開発フロー

1. 詳細仕様を検討する。
2. `docs/` の該当ファイルを更新する。
3. 未確定事項がある場合は、本文に状態を明記するか `docs/tasks/` に切り出す。
4. `docs/api/` や `docs/design/` を変更した場合は、`src/shared/` の型・schema と照合する。
5. 仕様に基づいて実装する。
6. 実装後に仕様とのズレがないか確認する。

## 参照単位

実装判断では、次の分割仕様を参照する。

- `docs/product/`: プロダクト概要、ユースケース、MVP スコープ、成功判定。
- `docs/design/`: ユーザー体験、状態機械、ロール、調査、メモ出力、ガードレール、プライバシー。
- `docs/api/`: LLM 呼び出し単位、JSON schema、バリデーション。
- `docs/prompts/`: LLM 呼び出しごとのプロンプト契約と草案。
- `docs/tasks/`: 未決事項、次に作る成果物、マイルストーン。
